# 需求说明

## 一、业务背景

主角是「花漾 Bloom」——一家布局沪、杭、宁、苏四城、8 家门店 + 4 个线上渠道的连锁花店。

**过去的做法**：一套 Qt 桌面端的订单管理程序（本项目的前身 `../huadian`），
能录单、改状态、配促销，数据存在内存里，做完就没了。

**遇到的问题**（也是所有线下连锁的通病）：

1. 老板月底才看到总营业额，不知道钱是"哪个节日、哪个渠道、哪个品类"挣的；
2. 采购靠店长经验，情人节备货多了烂在冷库，清明白菊备少了被投诉；
3. 促销活动做完就算，没人算 ROI，第二年还在重复同样的折扣力度；
4. 会员体系有等级，但没人知道哪些客户值得维护、哪些已经流失；
5. 线上四个平台各有一套后台，佣金、退款、履约数据散落，无法横向比较。

**要解决的核心矛盾**：**有交易数据，没有分析能力。**

---

## 二、项目目标

建设一套「花店全渠道经营数据分析平台」，实现：

| 目标 | 验收标准 |
| --- | --- |
| 数据可沉淀 | 交易数据从桌面程序迁移到 MySQL，并建立可扩展的数仓模型 |
| 数据可信 | 建立质量规则与对账机制，清洗后与业务库金额 100% 一致 |
| 分析可解释 | 能拆解节日/渠道/品类/客户对业绩的贡献，且每个数字可下钻到明细 |
| 结论可行动 | 输出带建议的经营分析报告，而不是一堆图 |
| 过程可复现 | 一条命令生成数据、一条命令建仓，任何人 clone 后能跑出同样结果 |

---

## 三、用户与使用场景

| 角色 | 关注点 | 使用方式 |
| --- | --- | --- |
| 老板 / 店长 | 今天卖了多少、同比如何、哪个店拖后腿 | 看板首页 KPI + 门店对比 |
| 运营 | 活动效果、渠道 ROI、优惠券核销 | 促销分析页 + 渠道对比 |
| 采购 / 花艺师 | 哪些花材卖得快、损耗多少、要不要补货 | 库存与商品分析 |
| 市场 / 会员运营 | 高价值客户是谁、哪些快流失 | RFM 分层 + 客户明细 |
| 数据分析师（本人） | 取数、建模、出报告 | SQL + Python + 报告导出 |

## 四、功能需求

### 4.1 数据层（第 1 轮已完成）

| 编号 | 需求 | 实现 |

### 4.3 分析建模（第 3 轮）

| 编号 | 需求 | 方法 |
| --- | --- | --- |
| F13 | 经营总览与趋势 | 同比/环比、STL 季节分解、指标树归因 |

## 五、非功能需求

| 类别 | 要求 | 落地方式 |
| --- | --- | --- |
| 可复现 | 同配置必得同数据 | 固定随机种子 + manifest 记录参数 |
| 可移植 | 换机器能跑 | 依赖固定、路径全由 `config.py` 推导、无绝对路径 |
| 安全 | 不出现明文密码 | `.env` 存专用账号，密码随机生成，`.gitignore` 排除 |
| 性能 | 全量装载 + 建仓 < 10 分钟 | 批量 INSERT、`FOREIGN_KEY_CHECKS=0`、预聚合 |
| 幂等 | 重复执行结果一致 | 全部 `TRUNCATE + INSERT` / `CREATE OR REPLACE` |
| 可维护 | 改口径只改一处 | 指标口径进视图/函数，不散落在脚本里 |
| 编码 | 中文不乱码 | 全链路 utf8mb4，CSV 用 utf-8-sig 兼容 Excel |

## 六、范围边界（明确不做什么）

- **不做**真实支付、物流对接（无外部依赖，专注数据链路）；
- **不做**多租户与权限系统（个人项目，避免过度设计）；
- **不做**实时流处理（离线 T+1 已能覆盖经营分析场景，实时留作扩展方向）；
- **不使用**真实客户数据（全部模拟生成，规避隐私问题）。

## 七、验收方式

1. 按 README「四步跑通」执行，全部脚本返回码为 0；
2. `python run.py check` 8 项校验全部通过（差额 = 0、孤儿行 = 0）；
3. `ads_kpi_monthly` 有 35 个月数据，GMV 与业务库对得上；
4. 看板能按日期/渠道/门店筛选并联动（第 4 轮）；
5. 报告能一键导出，图表与结论一致（第 5 轮）。
