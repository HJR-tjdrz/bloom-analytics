# ER 图与关系建模

## 一、建模原则

| 原则 | 本项目做法 |
| --- | --- |
| 三范式（3NF） | 业务库按 3NF 拆分：客户、商品、订单、明细各自独立，避免冗余更新异常 |
| 主键选择 | 用**业务编号**（`order_id`/`sku_id`/`customer_id`）做业务库主键，便于与上游系统对账；数仓侧另建**代理键**（`*_sk`） |
| 外键约束 | 关键关系（订单→客户/门店/渠道、明细→订单、BOM→花束/花材）建外键，防止脏数据写入 |
| 金额类型 | 一律 `DECIMAL(12,2)`，禁止 `FLOAT/DOUBLE`（0.1+0.2≠0.3 的经典坑） |
| 枚举字段 | 用 `VARCHAR + COMMENT` 而不是 `ENUM`，便于扩展新状态（`ENUM` 加值要改表结构） |
| 时间字段 | `DATETIME`（业务时间）+ `created_at`（入库时间）分离，便于排查时区问题 |
| 软删除 | 客户/商品用 `is_active` / `status` 标记，不做物理删除（保历史可追溯） |

## 三、关系矩阵（谁关联谁、为什么）

| 关系 | 基数 | 业务含义 | 为什么这样设计 |
| --- | --- | --- | --- |
| 客户 → 订单 | 1 : N | 一个客户多次购买 | 复购分析、RFM 的基础 |
| 门店 → 订单 | 1 : N | 每单由一个门店履约 | 门店业绩对比、人效坪效 |
| 渠道 → 订单 | 1 : N | 订单归属一个渠道 | 渠道 ROI、佣金成本核算 |
| 订单 → 明细 | 1 : N | 一单多件商品 | 商品结构分析的最小粒度 |
| 明细 → 花束/SKU | N : 1 | 明细可能是成品花束，也可能是散卖花材 | 两种粒度统一进一张明细表，用 `product_type` 区分 |
| 花束 → BOM | 1 : N | 一束花由多种花材组成 | **成本与库存还原的关键** |
| 订单 ↔ 促销 | M : N | 一单可命中多个活动 | 用 `order_promotions` 关联表记录每个活动的优惠贡献 |
| 订单 → 退款 | 1 : 0..1 | 已退款订单产生一条退款单 | 退款率、退款原因分析 |
| 订单 → 状态日志 | 1 : N | 状态每次变更记一条 | 履约时效（付款→制作→配送→完成）分析 |
| 花材 → 每日库存 | 1 : N | 每个花材每天一条快照 | 周转率、损耗率、缺货分析 |

## 四、业务库 → 数仓的模型演进

业务库是「为写入优化」的 3NF 结构，直接拿来做分析会有三个问题：

1. **JOIN 太多**：算一个月度 GMV 要连 5 张表，看板每次刷新都扫全表；
2. **历史状态丢失**：客户改了会员等级，历史订单的等级权益就跟着变了；
3. **口径不统一**：不同人写 SQL，"GMV" 有人含运费、有人不含。

所以数仓侧做了三件事：

| 业务库 | 数仓 | 变化原因 |
| --- | --- | --- |
| `orders` + `order_items`（两张表、算子要 JOIN） | `fact_sales`（明细宽事实，维度键已就位） | 分析只扫一张表 |
| `customers.member_level`（只有当前值） | `dim_customer`（SCD2 多版本） | 历史订单要按当时等级算权益 |
| 无日期维表 | `dim_date`（含节假日/节日/需求指数） | 所有趋势分析都要按"业务日"分组 |
| SKU 与花束两张表 | `dim_product`（统一商品维） | 事实表只能有一种粒度 |

**代理键（surrogate key）的作用**：
业务编号（如 `C000123`）可能因系统迁移而变化，而代理键 `customer_sk` 永不变，
事实表只存代理键，维度属性变化不影响历史事实——这是数据仓库稳定性的基石。
