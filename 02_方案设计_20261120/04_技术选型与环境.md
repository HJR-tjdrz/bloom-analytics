## 二、逐层选型理由

### 2.1 为什么用 MySQL 做数仓，而不是 Hive / ClickHouse / Doris？

| 方案 | 优点 | 为什么本项目不用 |
| --- | --- | --- |
| **MySQL 8.0** | 零部署成本、团队人人会用、JD 里高频出现 | ✅ 采用：10 万单量级完全够用，能完整演示分层建模、索引优化、存储过程 |
| Hive / Spark | 大数据量、离线批处理标准 | 需要 Hadoop 集群，个人电脑跑不动，属于"为了技术而技术" |
| ClickHouse | OLAP 查询极快 | 学习成本高、SQL 方言差异大，且 10 万行数据体现不出优势 |
| PostgreSQL | 窗口函数更强 | 用户岗位 JD 明确写 MySQL，优先匹配招聘要求 |

**结论**：数据量级决定架构，10 万单的分析场景，MySQL + 分层设计 + 索引优化
已经是"正确的工程判断"，硬上大数据组件反而是减分项。

> 面试话术：如果数据量涨到 10 亿行，我会把 DWD 层迁到 Hive/Spark，
> ADS 层用 ClickHouse 或 Doris 提供亚秒级查询，MySQL 只保留 OLTP——
> **架构要跟着数据量走，不是跟着时髦走**。

### 2.2 为什么 OLTP 与 OLAP 分两个库？

| 维度 | `bloom_oltp` | `bloom_dw` |
| --- | --- | --- |
| 优化目标 | 写入快、事务强一致 | 大范围扫描快 |
| 表结构 | 3NF，少冗余 | 星型模型，适度冗余 |
| 索引 | 主键 + 少量业务索引 | 组合索引 + 覆盖索引 |
| 更新方式 | 行级增删改 | 每日全量重跑（幂等） |
| 权限 | 应用账号读写 | 分析账号读、ETL 账号写 |
| 跑批影响 | 无（物理隔离） | 可独立扩容 |

### 2.3 为什么不用 ORM（SQLAlchemy）？

- 项目要展示的是 **SQL 能力**：建表、索引、视图、存储过程、执行计划、分区；
- ORM 会把 SQL 藏起来，反而不利于表达"我会写 SQL"；
- 但也没有裸写字符串拼接——`db.py` 做了连接上下文、参数化查询、批量装载、契约校验的封装，
  **既保住 SQL 控制权，又有工程规范**。

### 2.4 为什么前端用原生 HTML/CSS/JS + ECharts？

| 方案 | 取舍 |
| --- | --- |
| **原生 + ECharts** | ✅ 零构建、离线可用（ECharts 本地化）、clone 即跑、面试官打开就能看 |
| Vue3 + Vite | 更"现代"，但需要 npm 装依赖 + 构建产物，README 部署步骤变长 |
| React + AntD | 对这个体量的 BI 看板属于过度工程 |

**判断依据**：这个项目的重点是"数据"，不是"前端工程化"。
用最轻的技术把图做好看、把交互做顺，才是对的选择。

### 2.5 为什么数据用"生成"而不是找公开数据集？

- 公开数据集（Kaggle 花店/零售）**没有花束 BOM、没有节日促销、没有损耗**，
  业务纵深不够，分析只能做表面功夫；
- 自建生成器的好处：**业务规则可解释**（每个数字都能说出为什么）、
  **可复现**（固定种子）、**可注入脏数据**（清洗才有东西可洗）、
  **可扩展**（加一个节日、改一个渠道权重即可）；
- 代价是要写约 1,500 行生成器代码——但这本身就是"业务建模能力"的体现。

### 2.6 为什么用 SQL 视图 + 函数固化口径？

```sql
-- 反例：每个报表各写一遍
SELECT SUM(net_amount + freight_amount) FROM fact_sales WHERE status <> '已取消';

-- 正例：口径封装
CREATE VIEW v_daily_kpi AS SELECT ... ;   -- 所有人查这个
CREATE FUNCTION fn_profit_rate(...) ... ; -- 毛利率算法只有一份
```

好处：**改一处，全站生效**；坏处：视图嵌套过深会影响性能（本项目控制在 1 层）。

## 三、目录与路径约定

| 约定 | 原因 |
| --- | --- |
| 所有路径由 `bloom/config.py` 用 `Path(__file__).parents[...]` 推导 | 从任意工作目录启动都能找到文件，不写死绝对路径 |
| 代码文件名用英文，目录与文档用中文 | Windows 命令行对中文路径编码不友好；文档中文更易读 |
| 数据文件 `utf-8-sig` | Excel 双击打开不乱码（运营同学会用 Excel 看） |
| 日志写 `logs/` 并按天分文件 | 排查问题有据可查，且已 gitignore |

## 四、已知风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| MySQL 未启动 | 连接被拒绝 | `db.py` 捕获异常并给出三步排查提示 |
| root 密码错误 | 初始化失败 | 明确提示"确认密码/端口/服务状态"，不吞异常 |
| 中文乱码 | 控制台显示 `????` | 全链路 utf8mb4 + `sys.stdout.reconfigure(encoding='utf-8')` + `.bat` 里 `chcp 65001` |
| 重复执行导致数据翻倍 | 行数变 2 倍 | 全部 `TRUNCATE + INSERT`，幂等 |
| 端口 3306 被占用 | 连不上 | `.env` 里可改 `MYSQL_PORT` |
| 依赖安装慢/失败 | pip 超时 | 已配置阿里云镜像；`--no-cache-dir` + 指定 `TEMP` 目录规避权限问题 |
| 磁盘空间 | H 盘剩余约 11 GB | 数据约 60 MB，MySQL 数据约 200 MB，充足 |
