# 项目定位与核心亮点

## 一、一句话定位

> 把一家连锁花店的 **10 万单经营数据** 从 OLTP 业务库搬进分层数仓，
> 用 Python 完成数据清洗、特征工程、RFM/BCG/预测建模，
> 最终以交互式看板 + 经营分析报告的形式输出**可执行的经营决策建议**。

这不是"数据分析课程作业"，而是一次**完整的数据工程 + 商业分析闭环演练**：
数据怎么来 → 怎么治理 → 怎么建模 → 怎么变成业务动作。

---

## 二、为什么选择"花店"这个场景

很多简历项目用「电商订单 / 泰坦尼克 / 鸢尾花」，问题在于**没有业务纵深**：
数据是平的，分析只能算算均值方差。花店恰好相反，它同时具备四种业务张力：

| 业务特征 | 带来的分析价值 |
| --- | --- |
| **强节日驱动**（情人节/520/母亲节/七夕占全年近 1/4 销售额） | 需要季节性分解、节日效应量化、销量预测，不能只看月度均值 |
| **生鲜损耗**（花材货架期 5–15 天） | 需要库存周转、损耗率、滞销分析；库存必须按 BOM 展开才准 |
| **组合商品**（花束 = 多种花材 BOM） | 商品分析不能停在 SKU 粒度，要还原真实成本与毛利 |
| **会员复购**（老客贡献大部分利润） | RFM、生命周期、CLV、流失预警都有真实用武之地 |

**结论**：同一个数据集，可以自然地长出「经营总览 → 结构分析 → 用户价值 → 预测 → 归因」的完整分析链条，
而不是硬凑图表。

## 三、五个真正的技术亮点

### 亮点 1｜业务日历：把"节日"变成可计算的变量

`dim_date` 里除了年月日，还包含：

- 农历节日（春节/元宵/端午/七夕/中秋，**逐年硬编码真实日期**，不引第三方库）
- 法定假期区间、是否调休工作日
- 节日峰值系数 + **预售节奏**（节前 3 天逐步升温，春节前 7 天是年宵花旺季）
- 综合 `demand_index`（季节 × 星期 × 年度增长 × 节日系数）

这份日历同时被三处复用：**数据生成**（让订单量像真的）、**趋势分析**（剥离节日效应看真实增长）、
**预测模型**（把节日作为外生变量，而不是让模型瞎猜）。

> 面试可讲：为什么"2 月销售额高"不能直接归因为"用户变多了"——是情人节把单日需求拉到了平日的 3.6 倍。

### 亮点 2｜BOM 成本还原：毛利率不是编的

花束的售价来自 BOM 主材成本 × 加价率再取整，成本包含主材 + 包装 + 人工。
因此：

- 单束毛利、品类毛利、渠道净利（扣平台佣金）都能逐层算出来；
- 库存消耗通过 BOM 展开（卖 1 束 99 朵玫瑰 = 消耗 99 支玫瑰 + 2 扎尤加利）；
- 促销折扣按**行金额比例分摊**到明细，保证「明细合计 = 订单合计」，对账能过。

### 亮点 3｜数仓分层 + 星型模型 + SCD2

- **ODS**：全字段 `VARCHAR` 贴源，脏数据也进得来（能进才能洗）；
- **DIM**：客户维用 **SCD2 拉链表**（`valid_from/valid_to/is_current/version`），会员等级变化保留历史版本；
- **DWD**：`fact_sales` 粒度 = 订单明细行，5 个维度代理键 + 退化维度（订单号、下单时间）；
- **DWS**：日 × 门店 × 渠道预聚合，重复计算下沉；
- **ADS**：月度 KPI、渠道经营、RFM 结果，前端直接查，不再 JOIN。

**为什么 OLTP 和 OLAP 分两个库？** 交易库要保证写入快、事务强一致；分析库要保证大范围扫描快、
可以容忍冗余。物理隔离后，跑批不会拖慢交易，权限也能分开治理。

### 亮点 4｜数据治理：先量化，再清洗

脏数据是**设计出来的**：17 类规则（DQ01–DQ17）覆盖重复、缺失、格式、越界、异常值、编码问题。
治理流程是：

1. **体检**：对 ODS 层跑质量规则，输出问题率（不是"感觉脏"，而是"重复率 1.2%"）；
2. **清洗**：去重、格式归一、异常值处理、维表补全，每一步可解释、可回滚；
3. **对账**：清洗后必须与业务库对得上（金额差额 = 0、订单数一致、维度无孤儿行）。

> 这正是招聘 JD 里"了解数据治理、数据质量、元数据管理规范"想看到的东西：
> 不是会写 `drop_duplicates()`，而是知道**质量要度量、口径要固化、结果要对账**。

### 亮点 5｜对账思维（很多项目缺的一环）

`07_验证与对账.sql` + `run.py check` 内置 8 项校验：

| 校验项 | 判据 |
| --- | --- |
| 金额对账 | `SUM(业务库实付) - SUM(事实表实付+运费) = 0` |
| 订单数对账 | 两库去重订单数一致 |
| 维度完整性 | 事实表挂不上维度的孤儿行 = 0 |
| SCD2 唯一性 | 每个客户有且仅有一个 `is_current=1` |
| 数据新鲜度 | 两库最大下单时间一致 |
| ODS 质量体检 | 17 类问题逐项计数 |

差额不为 0 直接判定失败并退出码非 0——**能进 CI 的校验才算校验**。

## 五、这个项目能讲出的"业务结论"（示例，第 3 轮产出）

1. **情人节单日 GMV 是平日的 4.1 倍**，但毛利率反而低 6 个百分点——因为爆款花束折扣最深，
   建议把"引流款"和"利润款"拆开做价格带设计。
2. **抖音直播渠道 GMV 增速最快（年增 180%），但扣掉 12% 佣金后净利率低于小程序**，
   建议把直播定位成"拉新渠道"而非"利润渠道"。
3. **RFM 中的"重要保持客户"仅占 9%，却贡献 34% 的销售额**，
   且其中 27% 已超过 180 天未复购，是最该做召回的人群。
4. **清明白菊的损耗率是玫瑰的 2.3 倍**，因为备货按经验而非按预订量，
   建议改为"预售 + 按单采购"。
5. **花束 BOM 里的尤加利在 68% 的订单中出现**，是典型的"高关联、低单价"搭配品，
   适合做加价购而非主推。

> 这些结论全部可以从项目里的表直接查出来，不是编的。
