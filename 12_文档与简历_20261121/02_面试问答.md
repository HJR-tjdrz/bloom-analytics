## A. 数据建模（6 问）

**1. 为什么分业务库和数仓库两个库？**
交易库要保证写入快、事务强一致；分析库要保证大范围扫描快、可容忍冗余。
物理分离后跑批不影响交易，权限也能分开治理。`bloom_oltp` 16 张 3NF 表，`bloom_dw` 是分层数仓。

**2. 为什么要分 ODS / DWD / DWS / ADS 四层？**
ODS 保原始（脏数据也要能进，出问题能追溯）；DWD 保证口径唯一（清洗一次全公司用）；
DWS 把高频聚合下沉（看板快 10 倍）；ADS 直接服务报表（前端零 JOIN）。
每层解决一个问题，不分层就会"每个报表一套 SQL、口径各不相同"。

**3. 星型模型和雪花模型怎么选？**
星型：维度不再拆，查询少 JOIN、快，适合 BI；雪花：维度规范化、省空间，但 JOIN 多。
本项目用星型（`fact_sales` + 6 个维度），因为分析场景查询性能优先。

**4. 什么是 SCD2？为什么客户维要用它？**
缓慢变化维的第二种处理：保留历史版本（valid_from / valid_to / is_current / version）。
客户会员等级会变，历史订单要按"下单当时"的等级算权益，否则去年订单会被今年的等级"改写"。

**5. 代理键和业务主键的区别？**
代理键（`customer_sk`）是数仓内部自增 ID，永不变；业务主键（`C000123`）可能因系统迁移变化。
事实表只存代理键，维度属性变化不影响历史事实。这是数仓稳定性的基石。

**6. 事实表的粒度怎么定？**
本项目定在**订单明细行**（`fact_sales` 一行 = 一个订单里的一件商品），这是最细的可加粒度，
所有上层指标都能由它聚合。粒度定粗了（比如按订单）就做不了商品分析。

## B. SQL 与优化（6 问）

**7. 你做过什么 SQL 优化？**
建仓 376 秒 → 9.8 秒。原因：`dim_date` 用 `full_date` 关联但没索引，1053 行的维表被当驱动表做全表嵌套；
加索引后执行计划从 `ALL/1053` 变成 `ref/1`。详见 `04_MySQL数仓_20261120/20_性能优化记录.md`。

**8. 怎么发现慢 SQL 的？**
两条路：① 在 `run_sql_file` 里给每条语句计时，>5 秒自动告警；② 用 `EXPLAIN` 看 `type`、`rows`、`Extra`。
`type=ALL` 或 `rows` 远大于结果行数，基本就是索引或 JOIN 顺序有问题。

**9. 覆盖索引是什么？项目里怎么用的？**
索引里包含查询需要的全部列，不用回表。
例如 `idx_fact_customer_cover (customer_sk, order_time, net_amount, order_status)`，
RFM 聚合只扫索引就够，IO 减半。

**10. 窗口函数用过哪些？**
`LAG`（7/28 天滞后）、`AVG OVER(ROWS BETWEEN ...)`（移动平均）、`NTILE`（分位分桶）、
`ROW_NUMBER`（去重取最新）、`RANKX` 思路（帕累托累计）。
用在 `dws_daily_features`（滞后与移动平均）和 RFM 打分（分位数）。

**11. 大表分页/去重怎么写？**
去重取最新：`ROW_NUMBER() OVER (PARTITION BY key ORDER BY ts DESC)` 再筛 `rn=1`；
`DISTINCT` 在宽表上代价高，能用窗口函数就用窗口函数。

**12. 事务和幂等怎么保证？**
所有建仓脚本"先 TRUNCATE 再 INSERT"，天然幂等；
存储过程里用 `START TRANSACTION` + `EXIT HANDLER FOR SQLEXCEPTION ROLLBACK` 保证失败不留半截数据。

## C. 数据治理（6 问）

**13. 你怎么定义"数据质量"？**
五个维度：完整性（该有的有没有）、唯一性（有没有重复）、有效性（格式/取值对不对）、
一致性（跨字段/跨表矛不矛盾）、及时性（时间在不在合理区间）。每维加权算总分。

**14. 质量分 99.61 是怎么算的？**
维度得分 = 1 − Σ(该维度违规行数) / Σ(表总行数)，再按维度权重加权（完整性 .25 / 唯一性 .20 /
有效性 .25 / 一致性 .15 / 及时性 .15）。唯一性用 `COUNT(*) - COUNT(DISTINCT 主键)` 精确算。

**15. 清洗时最难的取舍是什么？**
"要不要把分数洗到 100"。客户ID缺失只能置 UNKNOWN 占位、已完成单缺配送时间是**事实缺失**，
补任何值都会污染分析。选择"保留 + 打标 + 分析时排除"，并在报告里写清楚——**不制造假数据**。

**16. 怎么证明清洗没丢数据？**
三层对账：① 行数（清洗层 + 隔离表 = 业务库）；② 金额（差额 = 隔离订单金额，解释差 0.00）；
③ 逐字段（时间/状态/实付 100% 一致）。详见 `06_ETL与特征工程/03_对账报告.md`。

**17. 数据字典怎么保证不过期？**
不手工维护。从 `information_schema` 实时读表/字段/注释/类型/键，代码生成 MD + Excel，
表注释在建 DDL 时就写好。527 个字段永远是当前状态。

**18. 指标体系和指标有什么区别？**
指标是"数"，指标体系是"有层级、有口径、有责任人"的一套资产：
原子（GMV）→ 派生（近 12 月 GMV）→ 复合（客单价 = GMV/订单数）。
每个指标绑定唯一一段 SQL，改口径只改一处。

## D. 分析方法（7 问）

**19. RFM 怎么打分？为什么要用分位数？**
R/F/M 各用五分位打分（R 反向：越近越高分）。用分位数而不是拍阈值，是因为数据分布会变，
固定阈值（比如"消费>1000 算高"）过两个月就失效。

**20. 怎么验证分群是合理的？**
用 K-Means（k=4）对标准化后的 RFM 聚类，与 8 分群算 ARI（调整兰德指数）。
本项目 ARI=0.235（>0 表示优于随机），说明规则分群与数据自组织方向一致。

**21. 波士顿矩阵的横轴"相对份额"你怎么算的？**
严格 BCG 需要"自己份额 / 最大竞品份额"，单企业数据拿不到竞品。
本项目用"品类内相对份额（本商品销售额 / 品类第一）"代理，并在报告里明确标注这是代理口径。

**22. 为什么促销不给"增量 ROI"？**
活动与节日高度共线，节日本身有 3~4 倍自然增长，没有对照组就无法拆分。
所以只给"让利效率 = 活动毛利 / 让利金额"，并说明严格归因需要门店级 A/B 实验或合成控制法。

**23. 关联规则里 support / confidence / lift 分别是什么？**
support = P(A∩B)（同时出现的比例）；confidence = P(B|A)（买 A 的人里也买 B 的比例）；
lift = confidence / P(B)（比随机高多少倍）。lift ≤ 1 的规则没有意义。

**24. Apriori 为什么比暴力枚举快？**
先验性质：频繁项集的所有子集必然频繁。所以逐层剪枝——先找频繁 1 项集，
再由它组合成候选 2 项集，非频繁的直接淘汰，候选数量指数级下降。

**25. 预测为什么用 SARIMAX 不用 LSTM？**
数据只有 1,000 天出头，深度模型容易过拟合；SARIMAX 可解释（每个外生变量系数能讲业务含义），
且能直接吃"是否周末/节假日/节日"这类日历特征。业务要的是"下周备多少货"，不是炫技。

## E. 工程与可视化（5 问）

**26. 数据量只有 11 万行，为什么不用 Hive/Spark？**
数据量决定架构。11 万行用 MySQL + 分层设计 + 索引优化就够，硬上大数据组件是过度设计。
如果涨到 10 亿行，我会把 DWD 迁到 Hive/Spark，ADS 用 ClickHouse/Doris 提供服务。

**27. ETL 怎么保证可重跑？**
全部"先清空再插入"，`CREATE OR REPLACE VIEW`、`DROP ... IF EXISTS`；
数据生成固定随机种子，同一份配置每次结果一致。跑多少次结果都一样。

**28. 为什么前端用原生 JS + ECharts，不用 Vue/React？**
项目重点是数据不是前端工程化。零构建 = clone 下来双击就能看，面试官不用装 Node。
代价是没有组件化，但 6 个页面的复杂度完全可控。

**29. 看板为什么深色、报告为什么浅色？**
看板在屏幕上长时间看，深色减少眩光；报告要打印/发邮件/贴进 Word，浅色更合适。
同一个项目两种主题不是不一致，而是**按使用场景做设计**。

**30. 这个项目如果重做，你会改什么？**
三点：① 加调度（Airflow/Windows 计划任务）让链路自动跑；② 促销做门店级 A/B 实验，才能算真增量 ROI；
③ 把质量规则做成配置表（现在写在代码里），让业务方也能加规则。

## 附：三个"送命题"的应对

**Q：这些数据是真的吗？**
A：是模拟数据，但生成规则是可解释的（节日系数、复购分布、BOM 成本都写在代码里）。
用模拟数据是因为真实花店数据涉及隐私，而且公开数据集没有花束 BOM 和节日促销，做不出业务纵深。

**Q：你一个人做的？做了多久？**
A：独立完成。核心链路约 5 轮迭代，每轮都有可验证的产出（数仓跑通 → 治理报告 → 分析报告 → 看板 → 报告生成）。
代码约 6,000 行 Python + 2,000 行 SQL/前端。

**Q：这个项目最难的地方？**
A：不是写代码，是**判断"什么算对"**。比如"准时送达率 62%"看着像数据问题，实际是生成逻辑写错了延迟区间；
"企业客户 GMV 占比 0%"查下去是客户池下标用错。这类 bug 不报错，只能靠业务常识发现。
