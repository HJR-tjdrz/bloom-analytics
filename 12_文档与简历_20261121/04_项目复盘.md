# 项目复盘

> 写给自己看的：哪些做对了、哪些踩坑了、下次怎么做得更好。
> 面试时被问"你从这个项目学到什么"，这里就是答案。

---

## 一、五个真实踩过的坑

| # | 坑 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | MySQL 保留字 | `CREATE TABLE dim_date` 报 1064 | `YEAR_MONTH` 是保留字 | 25 处改名 `month_key`，并写脚本比对 261 个保留字 |
| 2 | 跨库视图 | `Table 'bloom_dw.orders' doesn't exist` | 视图建在 dw 库却引用未限定库名的 oltp 表 | 5 张表加 `bloom_oltp.` 前缀 + 写跨库引用检查器 |
| 3 | 维表缺索引 | 建仓 376 秒 | `dim_date.full_date` 无索引，1053 行维表当驱动表 | 补索引 → 9.8 秒（38 倍） |
| 4 | 企业客户消失 | 企业 GMV 占比 0.00% | 客户池企业客户在尾部，分配器从下标 0 取 | 从 `ent_start` 开始取 |
| 5 | 准时率异常 | 准时送达率仅 62.5% | "不迟到"分支的延迟取了 `[-60,30)`，凭空造出 30% 迟到 | 改成 `[-120,0]` |

**共同点**：后三个都**不报错**。代码跑得通、数字也在"能用"的范围，
只有拿业务常识去校验（企业客户怎么可能为零？花店怎么可能 40 年周转一次？）才能发现。

> 这条经验写进了简历：**"能跑通"和"对"是两件事，数据分析师要对数字有嗅觉。**

## 二、三个做对了的决定

### 1. 先做数据工厂，再谈分析

很多同学的项目卡在"没有数据"。我花了两天做生成器（日历、BOM、促销、脏数据注入），
后面所有分析都建立在一份"有业务规律"的数据上——节日有峰值、客户会复购、花材会损耗。
**能做分析的前提是数据有结构，不是数据有多干净。**

### 2. 把"口径"当产品做

指标、标签、数据字典全部代码生成，而不是写 PPT。
好处是：数据一变，文档自动更新；面试官问"这个数怎么算的"，我能直接指出哪段 SQL。

### 3. 敢说"算不了"

促销 ROI 那条，我一开始想硬算"增量 GMV / 折扣成本"，后来发现活动全在节日，
节日本身有 3~4 倍自然增长，没有对照组根本拆不开。最后改成"让利效率"并写明边界。
**这比给一个漂亮但站不住的数更专业。**

## 三、如果重做，会改什么

| 改进项 | 为什么 |
| --- | --- |
| 加调度（Airflow / Windows 计划任务） | 现在是手动跑，真实项目要每天自动更新 |
| 质量规则配置化（存表里） | 现在规则写在 Python 里，业务方加不了规则 |
| 促销做门店级 A/B | 才能算真正的增量 ROI，而不是相关性 |
| 增量更新而非全量重跑 | 现在每次 TRUNCATE 全量，数据涨到千万级就不行了 |
| 加数据血缘图 | 指标 → 表 → 源表的依赖关系，现在只有文档描述 |

## 五、给下一个项目的三条建议

1. **先想清楚"给谁看"**：这个项目的每份产出都对应一个角色（老板看报告、运营看 RFM、店长看库存），
   所以不会做成"图表堆砌"。
2. **留证据**：性能优化的前后对比、清洗的对账、规则的命中数——这些都是面试时最有力的材料，
   而且**只有当时记下来才留得住**。
3. **控制范围**：五轮迭代、每轮有可验证产出，比一次性写 2 万行代码然后跑不起来强得多。
