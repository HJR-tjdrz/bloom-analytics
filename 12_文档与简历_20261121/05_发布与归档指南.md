## 六、Zenodo：两种玩法

### 方案 1（推荐）：GitHub ↔ Zenodo 自动归档，发 Release 即出 DOI

**原理**：Zenodo 监听你的 GitHub 仓库，你每发一个 Release，它就自动把该版本的源码打包存档，
并分配一个 DOI。以后改代码发新 Release，就多一个新版本 DOI。

#### 步骤

1. **注册并登录 Zenodo**：<https://zenodo.org/>（可用 GitHub 账号直接登录）
2. **授权 GitHub**：右上角头像 → `Settings` → 左侧 `GitHub` → 点 **Connect**
   → 跳转 GitHub 授权页 → 选择你的仓库（或 All repositories）→ Authorize
3. **打开仓库开关**：回到 Zenodo 的 GitHub 页面，找到 `bloom-analytics`，
   把开关从 `OFF` 拨到 **`ON`**
   > ⚠️ 顺序很重要：**必须先拨开关，再发 Release**。先发 Release 不会触发归档（只能手工补一个）。
4. **在 GitHub 创建 Release**：
   - 仓库页 → 右侧 `Releases` → `Create a new release`
   - Tag：`v1.0.0`（点 "Create new tag on publish"）
   - Title：`BloomAnalytics v1.0.0`
   - Description：从 `CHANGELOG.md` 复制 v1.0.0 那段
   - 点 **Publish release**
5. **等 1~2 分钟**，回 Zenodo 的 GitHub 页面刷新，会看到一条新记录，带 DOI 徽章：
   ```
   DOI: 10.5281/zenodo.1234567
   ```
6. **完善元数据**：点进该记录 → `Edit` →
   - 确认标题、作者（用真实姓名 + 单位）、关键词
   - 资源类型选 **Software**
   - License 选 **MIT License**
   - 关联标识符填 GitHub 仓库地址
   - 保存

> `.zenodo.json` 会自动提供这些元数据（见第七节），但**首次仍需人工核对**。

#### 拿到 DOI 之后

在 README 顶部加徽章：

```markdown
[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.1234567.svg)](https://doi.org/10.5281/zenodo.1234567)
```

在简历/报告里写：

> 开源项目，Zenodo 归档 DOI: [10.5281/zenodo.1234567](https://doi.org/10.5281/zenodo.1234567)

**两个 DOI 的区别**（Zenodo 会给两个）：

| 类型 | 示例 | 含义 |
| --- | --- | --- |
| Concept DOI | `10.5281/zenodo.1234566` | 指向"整个项目"，永远指向最新版 |
| Version DOI | `10.5281/zenodo.1234567` | 指向 v1.0.0 这个具体版本 |

引用具体版本用 Version DOI；"这个项目"整体引用用 Concept DOI。

### 方案 2：直接上传 ZIP 到 Zenodo（不依赖 GitHub）

适合：不想公开 GitHub、或只想留一个存档快照。

> 📦 **已经帮你打好包**：`H:\花店订单管理应用\发布包\bloom-analytics-v1.0.0_20261121.zip`
> （182 个文件、压缩后 3.0 MB，已自检确认**不含** `.env` / `.venv` / 数据 CSV / 日志）。
> 想自己重新打包，再用下面的命令。

1. 打包（**必须排除** `.venv`、`logs`、数据 CSV、`.env`）：
   ```powershell
   # 在项目根目录执行，生成到上一级目录
   Compress-Archive -Path (Get-ChildItem -Exclude '.venv','logs','.env','__pycache__','.pytest_cache' |
       Where-Object { $_.Name -notin @('clean','raw_export') }) -DestinationPath "..\bloom-analytics-v1.0.0.zip"
   ```
   > 更稳的做法：先复制一份干净副本，删掉不该传的目录，再压缩。
2. Zenodo → `New upload` → 上传 zip
3. 资源类型选 **Software**，填标题、作者、描述、关键词、License（MIT）
4. 点 **Publish** → 立即获得 DOI

**缺点**：以后更新代码要重新上传、DOI 会变，且与 GitHub 仓库没有关联。

## 七、已经准备好的三个元数据文件（上传前要改 3 处）

| 文件 | 作用 | 要改什么 |
| --- | --- | --- |
| `.zenodo.json` | Zenodo 自动读取的元数据（**仅对方案 1 生效**） | `creators[0].name` → 你的姓名；`affiliation` → 学校/单位；`related_identifiers[0].identifier` → 你的仓库地址 |
| `CITATION.cff` | GitHub 右上角显示 "Cite this repository" | `authors` 的姓名/单位/ORCID；`repository-code` / `url` 的仓库地址 |
| `CHANGELOG.md` | 版本说明，Release 描述可以直接复制 | 一般不用改 |

**3 处占位符**，全局搜索替换即可：

| 占位符 | 替换成 |
| --- | --- |
| `YOUR_NAME` / `YOUR_FAMILY_NAME` / `YOUR_GIVEN_NAME` | 你的名字（英文/拼音） |
| `YOUR_GITHUB_USERNAME` | 你的 GitHub 用户名 |
| `YOUR_SCHOOL_OR_ORG` / `YOUR_ORCID` | 学校/单位；有 ORCID 就填，没有可以删掉该行 |

> `CITATION.cff` 里的 `orcid` 字段如果留空会报格式错误，**没有 ORCID 就整行删掉**。

## 九、常见问题

**Q：能不能只传代码不传数据？**
可以，而且推荐——数据 CSV 已在 `.gitignore` 里。别人 clone 后跑 `python run.py gen` 就能复现同样的数据。
`03_..\data\sample\` 保留了每表前 200 行，方便直接看格式。

**Q：`.venv` 太大传不上去怎么办？**
本来就不该传。别人自己 `python -m venv .venv && pip install -r requirements.txt`。

**Q：Zenodo 归档后才发现代码有 bug？**
发一个新 Release（v1.0.1），Zenodo 会生成新 DOI；旧 DOI 永久指向旧版本，这正是科研归档的意义。

**Q：Zenodo 要求公开仓库吗？**
方案 1 要求仓库公开（否则 Zenodo 拿不到代码）。如果不想公开，只能用方案 2 手动传 zip。

**Q：DOI 有什么用？**
可被引用、可被检索（Google Scholar / OpenAIRE）、永久有效。简历上写 DOI 比写"GitHub 链接"更有分量，
因为它代表"这是一个被正式归档的作品"。

**Q：需要给仓库加开源协议吗？**
已经有 MIT（`LICENSE`）。没有协议 = 别人不能合法使用，所以**必须有**。
