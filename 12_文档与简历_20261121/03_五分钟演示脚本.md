# 5 分钟演示脚本

> 用途：面试现场/线上面试演示，或录一段 demo 视频。
> 原则：**先给结论，再给证据**；不逐页点，只讲 3 个最有说服力的瞬间。

---

## 准备（开始前 2 分钟）

```bash
cd H:\花店订单管理应用\最新项目
.venv\Scripts\python.exe run.py dashboard --port 5050
```

浏览器打开 `http://127.0.0.1:5050`，停在「经营总览」页。
另外准备好这三个文件夹窗口（随时可切）：

- `04_MySQL数仓_20261120/20_性能优化记录.md`
- `05_数据治理_20261120/03_数据质量报告.html`
- `09_经营分析报告_20261121/02_经营分析报告.html`

## 第 0–60 秒：一句话背景

> "这是一个花店经营分析平台。起点是我本科写的一个 C++/Qt 桌面版订单管理程序，
> 能录单但不能分析。我把它升级成了：MySQL 双库数仓 → 数据治理 → Python 分析建模 → ECharts 看板 → 自动报告。
> 数据是 3 年、11.6 万行订单明细，全部可复现。"

**屏幕**：停留在看板总览页，让它自己"亮"一下。

---

## 第 60–150 秒：讲架构（不看代码，看 README 架构图）

> "整体是五层：
> **业务库** 16 张 3NF 表；**数仓** ODS/DIM/DWD/DWS/ADS 五层，星型模型 + SCD2 客户维；
> **治理层** 18 条质量规则 + 数据字典 + 48 个指标 + 18 个标签；
> **分析层** 8 个模块；**应用层** 是看板和报告。
>
> 这里我做了一个判断：数据只有 11 万行，用 MySQL 分层 + 索引优化就够，上 Hive/Spark 是过度设计。"

---

## 第 150–240 秒：三个"硬"瞬间（重点）

### 瞬间 1：性能优化（打开 `20_性能优化记录.md`）

> "第一次建仓跑了 376 秒，明显不合理。EXPLAIN 发现 `dim_date` 是全表扫描还被当成驱动表——
> 1053 行的维表被嵌套 10 万次。补了 `full_date` 索引后，执行计划从 `ALL/1053` 变成 `ref/1`，
> **376 秒 → 9.8 秒，38 倍**。"

### 瞬间 2：数据治理（打开质量报告 HTML）

> "18 条规则在清洗前后各跑一遍：98.71 → 99.61。
> 但**我没有把分数洗到 100**——客户ID缺失只能置 UNKNOWN、已完成单缺配送时间是事实缺失，
> 补任何值都会污染分析。所以我选择保留 + 打标 + 分析时排除。
> 同时用对账证明清洗没丢数：金额差额恰好等于隔离订单金额，解释差 0.00。"

### 瞬间 3：分析结论（切到看板「商品结构」页，指着波士顿矩阵）

> "这是波士顿矩阵。有意思的是绣球：周转 81 天，但货架期只有 6 天——**13.6 倍**。
> 这说明损耗不是员工不细心，是订货模式的结构性问题。所以我给的建议是改预售制，不是加强管理。"

## 可能被追问的 5 个点（提前背）

| 追问 | 一句话回答 |
| --- | --- |
| 数据是真的吗 | 模拟数据，但生成规则可解释（节日系数/复购分布/BOM 成本都在代码里），真实数据涉及隐私且没有 BOM |
| 为什么不用 Tableau 做看板 | 看板要能嵌进业务系统，自建更灵活；Tableau 我也做了配套手册，用于业务自助分析 |
| RFM 分群为什么可信 | 用 K-Means 交叉验证，ARI=0.235，规则分群与聚类方向一致 |
| 促销到底有没有效 | 观测数据算不出因果增量（活动与节日共线），所以我只给"让利效率"，并说明需要 A/B 实验 |
| 这个项目最难的地方 | 不是写代码，是判断"什么算对"——企业客户占比 0%、准时率 62% 这类不报错的 bug，只能靠业务常识发现 |

## 演示禁忌

1. **不要一上来讲代码**：先讲业务问题和结论；
2. **不要逐页点完 6 个页面**：选 3 个瞬间讲透，剩下的让对方自己点；
3. **不要说"我做了一个 CRUD"**：这个项目的价值在"从数据到决策"的链路；
4. **被问到不会的，直接说不会**：然后补一句"我现在的思路是……"，比硬编强。
