# 03 · 数据工厂说明

## 一、这里有什么

```
03_数据工厂_20261120/
├── 01_generate_data.bat        # 一键生成（双击即可）
└── data/
    ├── clean/                  # 17 张干净表 → 装载进 bloom_oltp（业务库）
    ├── raw_export/             # 4 张脏表   → 装载进 bloom_dw.ods_*（贴源层）
    ├── sample/                 # 每表前 200 行 → 提交 GitHub 供预览
    └── manifest.json           # 行数、字段、脏数据注入清单、生成参数
```

**为什么数据不提交到 Git？**
`clean/` 与 `raw_export/` 合计约 60 MB，且完全可由代码复现。
仓库只保留 **生成器 + 200 行样本**，clone 后跑一条命令即可得到全量数据——
这既是工程规范，也避免仓库体积膨胀。

## 二、数据是怎么"长"出来的（业务规则）

### 2.1 日订单量 = 乘法模型 + 泊松抽样

```
当日订单量 ~ Poisson( BASE × 月季节 × 星期 × 年度增长 × 节日系数 )
```

| 因子 | 取值示例 | 业务依据 |
| --- | --- | --- |
| 月季节 | 2月1.32 / 5月1.28 / 7月0.80 / 12月1.24 | 情人节、520+母亲节、酷暑淡季、圣诞 |
| 星期 | 周六 1.38 / 周日 1.25 / 周二 0.90 | 周末是花店主场 |
| 年度增长 | 2024:1.00 → 2025:1.18 → 2026:1.32 | 门店扩张 + 线上增长 |
| 节日系数 | 情人节 3.6 / 520 3.0 / 七夕 3.1 / 春节当天 0.68 | 峰值与"门店冷清"都要模拟 |

**预售节奏**尤其重要：情人节订单不是当天集中爆发，而是节前 3 天逐日升温
（2/11: 1.78 → 2/12: 2.25 → 2/13: 2.82 → 2/14: 3.60）。
这直接影响"备货曲线"和"预测模型"的合理性。

### 2.2 节日 → 品类偏好

不同节日买的根本不是同一种花：

| 节日 | 主要品类权重 |
| --- | --- |
| 情人节 / 520 / 七夕 / 圣诞 | 爱情告白 62% · 节日限定 22% · 日常悦己 10% |
| 母亲节 / 妇女节 / 教师节 | 感恩祝福 58% · 日常悦己 18% |
| 清明节 | 祭扫追思 82%（白菊/黄菊） |
| 春节 / 中秋 / 元旦 | 节日限定 40% · 感恩祝福 26% · 开业庆典 18% |
| 平日 | 日常悦己 36% · 爱情告白 26% · 感恩祝福 22% |

这决定了「清明卖菊花、情人节卖红玫瑰」的品类结构会自然体现在数据里，
后续做品类分析、波士顿矩阵才有真实差异。

### 2.3 客户：72% 复购 + 帕累托分布

- 每单 72% 概率是老客复购，28% 是新客激活（新客的 `register_date` = 首单日期）；
- 老客按"忠诚度"分 10 个桶加权抽取（`np.random.beta(1.25, 3.2)`），
  形成典型的**帕累托效应**：少数客户贡献大量订单；
- 企业客户（800 家）单独管理，走「企业团购」渠道，买开业花篮、单量大、复购稳定。

### 2.4 渠道结构随时间演化

抖音直播从 2024 年初的 4% 涨到 2026 年的 20%，门店占比从 42% 降到 28%。
这样"渠道结构变化"的分析才有东西可讲（而不是各渠道占比永远不变）。

### 2.5 订单状态按"距今时长"分布

越近的订单越可能还在流程中：

| 距今天数 | 状态分布 |
| --- | --- |
| > 30 天 | 已完成 92.5% · 已退款 3.7% · 已取消 3.8% |
| 8–30 天 | 已完成 90% · 待配送 2% · 已退款 3.5% · 已取消 4.5% |
| 3–7 天 | 已完成 72% · 待配送 14% · 制作中 7% · 其他 |
| 0–2 天 | 已付款 45% · 制作中 35% · 待配送 15% · 已完成 3% |

这样看板的"今日订单"才不会全是已完成，符合真实业务体感。

### 2.6 BOM 驱动的成本与库存

- 花束成本 = Σ(BOM 用量 × 花材成本) + 包装 + 人工；
- 每日库存：把当天卖出的花束按 BOM **展开成花材消耗量**，再推进库存；
- 生鲜花材（货架期 < 900 天）有 2%–9% 的损耗，非生鲜（花瓶/贺卡）无损耗。

## 三、17 类脏数据（DQ01–DQ17）

脏数据只注入到 `raw_export/`，`clean/` 保持干净——两条链路的关系是：

```
clean（业务库真实状态） ──导出──> raw_export（脏） ──ODS──> 清洗 ──> DWD（应还原为 clean）
```

这样既能演示清洗能力，又能用 `clean` 做**对账基准**，验证清洗没有丢数据。

| 规则 | 问题 | 注入比例 | 影响字段 |
| --- | --- | --- | --- |
| DQ01 | 订单号重复（重复导出） | 1.2% | orders |
| DQ02 | 客户 ID 缺失（游客单） | 2.0% | orders |
| DQ03 | 时间格式不规范（Excel 转换/手工录入） | 1.0% | orders.order_time |
| DQ04 | 金额异常（负数/0/50 倍离群） | 0.6% | orders.payable_amount |
| DQ05 | 状态值不规范（空格/英文/中英混写） | 0.8% | orders.status |
| DQ06 | 城市名含空白/全角 | 1.5% | customers.city |
| DQ07 | 手机号非法 | 0.5% | customers.phone |
| DQ08 | 业务时间越界（1999 / 2030） | 0.3% | orders.order_time |
| DQ09 | 已完成缺配送时间 | 3.0% | orders.delivery_time |
| DQ10 | 备注乱码 / emoji | 0.5% | orders.remark |
| DQ11 | 商品价格异常（0 / 99999） | 5.0% | products.list_price |
| DQ12 | 客户重复（同手机号两条） | 0.8% | customers |
| DQ13 | 会员等级脏值（大小写/空格/别名） | 1.0% | customers.member_level |
| DQ14 | 明细重复行 | 1.0% | order_items |
| DQ15 | 数量非正（退货冲销） | 0.4% | order_items.quantity |
| DQ16 | 孤立明细（订单号缺失） | 0.3% | order_items.order_id |
| DQ17 | 单价为 0（赠品未打标） | 0.5% | order_items.unit_price |

**`manifest.json` 里会记录每类规则的实际命中行数**，作为数据质量报告的"标准答案"——
第 2 轮的质量引擎跑完后，要能复现这些数字，否则说明规则漏了。

## 四、怎么复现

```bash
# 方式一：双击
01_generate_data.bat

# 方式二：命令行
python run.py gen

# 方式三：代码里调用
from bloom.datagen import generate_all
tables = generate_all(persist=True, write_sample=True)
```

**改参数**（`.env`）：

```ini
BLOOM_SEED=20241118            # 换种子 = 换一套数据（结构不变）
BLOOM_DATA_START=2024-01-01
BLOOM_DATA_END=2026-11-18      # 数据截止日（"今天"是 2026-11-19）
```

**生成耗时**：约 70 秒（10 万单 + 36 万行附属数据 + CSV 落盘）。
