## 三、技术设计（5 个值得说的点）

### 3.1 前后端分离，但前端零构建

- Flask 只返回 JSON，不拼 HTML；
- 前端是**纯 HTML/CSS/JS + 本地 ECharts**，没有 npm、没有 webpack、没有构建产物；
- 好处：`clone` 下来双击 bat 就能看，面试官不用装 Node。

### 3.2 离线 ECharts

`vendor/echarts.min.js` 是下载到本地的 1 MB 文件（5.5.1）。
不引 CDN 的原因很实际：**GitHub 上的项目如果依赖 CDN，断网/内网环境就白屏**。

### 3.3 接口缓存（5 分钟）

看板切页会重复请求同一接口。`app.py` 里用 `functools.wraps` 写了一个
进程内 TTL 缓存，命中后响应从 **1.7 秒降到 ~10 毫秒**。
没有引入 Redis —— 单机单进程场景，一个字典足够，**不过度设计**。

### 3.4 懒加载 + 按需 resize

- 6 个页面初始 `display:none`，只在第一次切换时渲染（`state.rendered` 集合去重）；
- 隐藏容器里 `echarts.init()` 会拿到 0 宽高，所以必须"先显示、再 init、再 resize"，
  切换页面后统一调 `resizePage()` 修正尺寸；
- 窗口 resize 时只重排当前页，不重排全部（省 CPU）。

### 3.5 筛选只作用于"能承受"的页面

经营总览的筛选（日期区间 / 渠道 / 门店）是**实时查事实表**的，参数化 SQL；
其余 5 页读的是第 3 轮预计算的 ADS 结果表（全量口径），
切过去时筛选栏会自动置灰并显示「全量口径」徽标。

> 这是有意的取舍：**能实时就实时，扛不住就走预计算**，并且把口径差异明示给用户，
> 而不是让用户以为筛选对所有页面都生效。

## 四、怎么跑

```bash
# 方式一：双击
90_run_dashboard.bat        # 启动服务 + 自动打开浏览器

# 方式二：命令行
python run.py dashboard --port 5050
# 然后浏览器打开 http://127.0.0.1:5050
```

前置条件：第 1 轮（数仓）、第 2 轮（特征）、第 3 轮（分析结果表）已跑完。
如果 `ads_*` 表是空的，先执行 `python run.py analysis`。

确保不会出现"点了没反应"的空指针。

## 七、已知限制（写清楚比藏着好）

1. **没有登录与权限**：单机演示项目，不做过度的 RBAC；
2. **没有实时刷新**：数据是离线批处理结果，5 分钟缓存，不做 WebSocket 推送；
3. **筛选不跨页**：见 3.5，是取舍不是 bug；
4. **截图**：开发环境的沙箱禁止启动浏览器进程，仓库里的页面截图需要本机打开后自行截取
   （第 5 轮文档会预留图片位置）。
