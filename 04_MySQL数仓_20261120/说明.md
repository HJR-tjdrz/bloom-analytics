## 二、安全设计：不再有"root 密码写死在代码里"

```
┌────────────────────────┐
│ 用户输入 root 密码      │  ← getpass，不显示、不落盘、不进命令历史
└───────────┬────────────┘
            │ 仅用于执行 01~05 的 DDL
            ▼
┌────────────────────────┐        ┌───────────────────────────┐
│ 随机生成 24 位应用密码   │───────▶│ .env（已 gitignore）      │
└───────────┬────────────┘        └───────────┬───────────────┘
            │ 写入 CREATE USER               │ 运行时读取
            ▼                                ▼
     bloom_app@localhost             Python 用 bloom_app 连接
     （只对两个库有权限）              root 密码用完即弃
```

**最小权限**：`bloom_app` 只能访问 `bloom_oltp.*` 和 `bloom_dw.*`，
即使凭据泄露也拿不到服务器其他库。

## 三、OLTP 设计要点（02 文件）

1. **16 张表覆盖全业务**：供应商 → 花材 → 花束 BOM → 客户 → 订单 → 明细 →
   促销/券 → 退款 → 库存 → 履约日志，形成完整链路而不是孤立表；
2. **外键只建关键关系**：订单→客户/门店/渠道、明细→订单、BOM→花束/花材。
   订单→促销这类弱关系不建外键，避免批量装载时反复校验；
3. **中文注释全覆盖**：每个字段都有 `COMMENT`，是第 2 轮自动生成数据字典的原料；
4. **索引按查询场景建**：
   - `idx_order_time`：按时间范围查订单
   - `idx_order_store_channel`：门店 + 渠道组合筛选
   - `idx_item_order`：由订单追明细
   - `idx_cust_city/register/phone`：客户检索三件套
5. **状态用 `VARCHAR` 不用 `ENUM`**：`ENUM` 加值要 `ALTER TABLE`，线上变更风险高。

## 四、数仓设计要点（03 文件）

| 层 | 表数 | 关键设计 |
| --- | ---: | --- |
| ODS | 4 | 全字段 `VARCHAR`；带 `batch_id`/`load_time`；脏数据必须能进 |
| DIM | 6 | 代理键；`dim_customer` 用 SCD2；`dim_promotion` 含 sk=0 未知成员 |
| FACT | 1 | `fact_sales` 粒度 = 订单明细行，6 个维度键 + 7 个可加度量 |
| DWS | 1 | 日 × 门店 × 渠道，预聚合 13 个指标 |
| ADS | 4 | 月度 KPI / 渠道经营 / RFM / 商品表现（后两张第 3 轮填充） |

**未知成员（unknown member）**：`dim_promotion` 里插了一行 `promotion_sk = 0`、
名称"无促销"，订单没命中活动时挂到这里。这样事实表外键永远非空，
`JOIN` 不会因为 `NULL` 丢行——这是维度建模的标准做法。

> 注意：向 `AUTO_INCREMENT` 列显式写 0 需要 `NO_AUTO_VALUE_ON_ZERO` sql_mode，
> 脚本顶部已经设置好了。

## 五、索引与优化（04 文件）

### 5.1 补充索引

| 索引 | 表 | 服务的查询 |
| --- | --- | --- |
| `idx_order_status_time (status, order_time)` | orders | 客服按状态+时间捞单 |
| `idx_item_order_cover (order_id, product_type, quantity, line_amount)` | order_items | 追明细，覆盖索引免回表 |
| `idx_cust_city_register (city, register_date)` | customers | 城市客户列表 |
| `idx_fact_date_store_channel (date_key, store_sk, channel_sk)` | fact_sales | DWS 重建、看板下钻 |
| `idx_fact_customer_cover (customer_sk, order_time, net_amount, order_status)` | fact_sales | RFM 聚合（覆盖索引） |
| `idx_fact_product_cover (product_sk, net_amount, quantity, cost_amount)` | fact_sales | ABC/波士顿矩阵（覆盖索引） |

### 5.2 视图（口径固化）

| 视图 | 用途 |
| --- | --- |
| `v_order_detail` | 一行看懂一个订单（客户/门店/渠道/明细聚合） |
| `v_sales_detail` | 事实表 + 全部维度，临时取数直接用 |
| `v_customer_value` | RFM 的取数底表（首单/末单/频次/金额） |
| `v_daily_kpi` | 日经营指标，看板"今日/近7日/近30日" |

### 5.3 分区实验表

`fact_sales_part` 按年 RANGE 分区（`p2023/p2024/p2025/p2026/pmax`）。
用途：演示 **partition pruning**——查 2026 年数据只扫 `p2026` 分区。

```sql
EXPLAIN SELECT COUNT(*) FROM bloom_dw.fact_sales_part
WHERE date_key BETWEEN 20260101 AND 20261231;
-- 输出 partitions 列只有 p2026
```

| 对象 | 用途 | 亮点 |
| --- | --- | --- |
| `fn_price_band(price)` | 价格带划分 | 商品分析、波士顿矩阵统一口径 |

> 这三个对象也解释了「为什么函数比 `CASE WHEN` 好」：
> 价格带规则改了，只改函数，所有报表自动生效。

## 七、对账（07 文件）

| 检查项 | 判据 | 不通过意味着什么 |
| --- | --- | --- |
| 各表层行数 | — | 装载是否完整 |
| **金额对账** | `业务库实付 - 事实表实付 = 0` | JOIN 放大/丢行 |
| 订单数对账 | 去重订单数一致 | 明细关联错误 |
| 维度完整性 | 孤儿行 = 0 | 维表漏建/键映射错 |
| ODS 质量体检 | 17 类问题计数 | 与 `manifest.json` 对照 |
| SCD2 检查 | 每客户仅一个 `is_current=1` | 拉链逻辑错 |
| 月度 KPI | 35 个月 | 日期维覆盖不全 |
| 数据新鲜度 | 两库最大下单时间一致 | 增量同步延迟 |

运行：

```bash
python run.py check      # 或双击 12_validate.bat
```

失败会返回非 0 退出码，可直接挂到 CI。

## 八、常用排查 SQL

```sql
-- 1) 事实表体积与时间范围
SELECT COUNT(*) AS rows_, MIN(order_time), MAX(order_time) FROM bloom_dw.fact_sales;

-- 2) 哪些订单在业务库有、事实表没有（丢数排查）
SELECT o.order_id FROM bloom_oltp.orders o
LEFT JOIN bloom_dw.fact_sales f ON f.order_id = o.order_id
WHERE f.order_id IS NULL LIMIT 20;

-- 3) 维表是否有重复（会导致事实表行数放大）
SELECT customer_id, COUNT(*) c FROM bloom_dw.dim_customer
WHERE is_current = 1 GROUP BY customer_id HAVING c > 1;

-- 4) 查看执行计划（是否用到索引）
EXPLAIN SELECT customer_sk, SUM(net_amount) FROM bloom_dw.fact_sales GROUP BY customer_sk;
```

## 十、踩坑记录（真实调试过程，面试可讲）

### 坑 1：`YEAR_MONTH` 是 MySQL 8.0 保留字

第一版把"年月"字段命名为 `year_month`，执行到 `CREATE TABLE dim_date` 时报：

```
ERROR 1064 (42000): You have an error in your SQL syntax ...
near 'year_month VARCHAR(8) NOT NULL COMMENT '年月 yyyy-mm',
demand_index ...' at line 22
```

**原因**：`YEAR_MONTH` 出现在 `INTERVAL n YEAR_MONTH` 语法里，被 MySQL 列入**保留字**，
不加反引号不能直接做列名（`status`、`year`、`month`、`version` 这些是**非保留**关键字，可直接用）。

**解决**：全链路改名为 `month_key`（`dim_date`、`ads_kpi_monthly`、`ads_channel_monthly`、
4 个视图、存储过程、对账 SQL 共 25 处），并写了一个脚本把 **261 个 MySQL 8.0 保留字**
与全部表名/列名/索引名/视图名逐一比对，确认无残留。

**教训**：建表前先查保留字表，比事后改名省事得多；命名规范里应该有一条"避免 SQL 关键字"。

### 坑 2：注释也会被当成语句执行

SQL 文件末尾如果只有一行注释（如 `-- CALL xxx('2026-10');`），
按分号切分后会得到一条"纯注释语句"，直接执行会报 `Query was empty`。
**解决**：切分后过滤掉所有行都是注释的片段（`00_init_database.py` 与 `bloom/db.py` 各实现一份）。

### 坑 3：向自增列显式写 0 会被当成"自动生成"

维度表的"未知成员"需要 `promotion_sk = 0`，但 MySQL 默认把 0 视为"请自动分配"。
**解决**：建仓脚本开头设置 `SET SESSION sql_mode = '...NO_AUTO_VALUE_ON_ZERO'`。
