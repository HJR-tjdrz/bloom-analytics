# 性能优化实录（建仓 376 秒 → 9.8 秒）

> 这是一次真实发生在项目里的排查过程，保留了完整的证据链。
> 面试时被问"你做过什么优化"，可以直接讲这一段。

---

## 一、现象

第一次执行 `python run.py dw`，控制台输出：

```
13:04:05 | INFO | 执行 SQL 文件：06_构建数仓.sql（20 条语句）
13:10:21 | INFO | 数仓构建完成，耗时 376.4 秒
```

**11.6 万行**的事实表插入，跑了 **6 分 16 秒**，明显不合理。
按经验，这个量级应该在 10 秒以内。

此时数据是对的吗？对。8 项对账全部通过，金额差额 0.00。
所以这不是"数据问题"，是"执行计划问题"——**能跑对，但跑得慢**。

---

## 二、定位：用 EXPLAIN 看执行计划

我先只跑了事实表那段 JOIN 的 `EXPLAIN`：

```sql
EXPLAIN
SELECT dd.date_key, dc.customer_sk, dp.product_sk
FROM bloom_oltp.order_items i
JOIN bloom_oltp.orders o     ON o.order_id    = i.order_id
JOIN bloom_dw.dim_date dd    ON dd.full_date  = DATE(o.order_time)
JOIN bloom_dw.dim_customer dc ON dc.customer_id = o.customer_id AND dc.is_current = 1
JOIN bloom_dw.dim_product dp  ON dp.product_id  = COALESCE(i.bundle_id, i.sku_id)
LIMIT 1000;
```

**优化前**：

| 表 | type | 使用索引 | 扫描行数 rows | 说明 |
| --- | --- | --- | ---: | --- |
| `dd`（dim_date） | **ALL** | ❌ 无 | 1,053 | **全表扫描，而且被选为驱动表** |
| `dc`（dim_customer） | index | idx_dim_cust_id | 31,415 | 索引全扫 |
| `o`（orders） | ref | idx_order_customer | 3 | 正常 |
| `i`（order_items） | ref | idx_item_order | 1 | 正常 |
| `dp`（dim_product） | eq_ref | uk_dim_product | 1 | 正常 |

问题一眼看出来：**`dim_date` 是全表扫描，还被优化器当成了驱动表**。
后果是：1,053 个日期 × 逐个去扫 3 万行客户维 × 再去订单表找匹配，
产生了巨量中间结果集，最后才收敛到 11.6 万行。

---

## 三、根因

```sql
JOIN dim_dw.dim_date dd ON dd.full_date = DATE(o.order_time)
```

`dim_date` 的主键是 `date_key`（yyyymmdd 整数），
而关联条件用的是 **`full_date`（DATE 类型）**，这一列**没有任何索引**。

优化器只有两个选择：
1. 全扫 `dim_date`（1,053 行）当驱动表，再反向找订单 —— 它选了这个；
2. 扫订单表再去 `dim_date` 里找 —— 因为没索引，只能全扫日期表 10 万次，更糟。

**根本原因：维度表"小"不等于"不用建索引"。**
1,053 行听起来很小，但被嵌套 10 万次就是 1 亿次比较。

---

## 四、修复

```sql
ALTER TABLE bloom_dw.dim_date ADD INDEX idx_dim_date_full (full_date);
```

同步写进 `03_数仓分层建表.sql`，保证新环境初始化时就带上：

```sql
CREATE TABLE dim_date (
    ...
    PRIMARY KEY (date_key),
    KEY idx_dim_date_ym (month_key),
    KEY idx_dim_date_full (full_date)   -- 事实表按日期关联时必须命中
) ENGINE=InnoDB ...;
```

**优化后**：

| 表 | type | 使用索引 | 扫描行数 rows |
| --- | --- | --- | ---: |
| `dc`（dim_customer） | index | idx_dim_cust_id | 31,415 |
| `o`（orders） | ref | idx_order_customer | 3 |
| `dd`（dim_date） | **ref** | **idx_dim_date_full** | **1** |
| `i`（order_items） | ref | idx_item_order | 1 |
| `dp`（dim_product） | eq_ref | uk_dim_product | 1 |

`dim_date` 从 `ALL / 1053 行` 变成 `ref / 1 行`——每次关联是**一次索引查找**，不是一次全表扫。

## 五、结果

| 指标 | 优化前 | 优化后 | 提升 |
| --- | ---: | ---: | ---: |
| 数仓构建总耗时 | 376.4 s | **9.8 s（热缓存）/ 22.0 s（冷缓存）** | **17~38 倍** |
| 其中 fact_sales 插入 | ≈ 370 s | 6.3 s（热）/ ≈ 18 s（冷） | 20~59 倍 |
| 索引体积代价 | — | 新增 1 个二级索引（1053 行，几十 KB） | 可忽略 |

> 两次实测差异来自 **InnoDB 缓冲池冷热**：刚全量装载完（`run.py all` 连跑）时
> `orders`/`order_items` 的页还没完全驻留内存，插入会慢一些。
> 无论冷热，都在 20 秒级，已经可以接受（单条 11.6 万行 JOIN 插入），
> 因此不再进一步优化。

**整条链路（`python run.py all`）实测**：

| 阶段 | 耗时 | 说明 |
| --- | ---: | --- |
| 数据生成 | 35–70 s | 10 万单 + 36 万行附属数据 + CSV 落盘 |
| 装载业务库 + ODS | 43 s | 371,753 + 249,042 行 |
| 维度 + 数仓构建 | 10–22 s | 33 万行维度 + 11.6 万行事实 + 汇总 |
| 对账校验 | 5 s | 8 项检查 |
| **合计** | **约 2 分钟** | 从零到可分析状态 |

## 六、沉淀下来的工程习惯

### 1. 慢语句自动告警

在 `bloom/db.py` 的 `run_sql_file()` 里加了逐条计时：

```python
cost = time.time() - t0
if cost >= 5:
    log.warning("  ⏱ 第 %d 条语句耗时 %.1f 秒：%s", idx, cost, stmt[:70])
```

不用额外装 APM，跑批时自己就会把"异常慢的语句"喊出来。

### 2. 维表也要考虑索引

经验规则：

| 场景 | 是否建索引 |
| --- | --- |
| 事实表 JOIN 维表的关联列（`full_date`、业务编号） | ✅ 必须 |
| 维表作为过滤条件的高频列（`city`、`category`） | ✅ 建议 |
| 只有几十行、且从不出现在 JOIN 条件的配置表 | ❌ 可不建 |

### 3. 先看执行计划，再改代码

优化前先跑 `EXPLAIN`，看 `type` 和 `rows` 两列：
- `type = ALL` → 全表扫描，通常是问题所在；
- `rows` 远大于结果行数 → JOIN 顺序或索引有问题；
- `Extra` 出现 `Using join buffer (hash join)` + 大 `rows` → 中间结果集过大。

### 4. 优化要有前后对比数字

"优化了性能"不是结论，"376 秒降到 9.8 秒，因为补了 full_date 索引，
执行计划从 ALL/1053 变成 ref/1"才是结论。

## 七、顺带发现的一个"假异常"

第一次跑对账时，脚本报 `验证结论：存在异常 ✗`，但逐项看数据其实全对。
原因是校验逻辑写得过于粗暴：只要列名里带"缺失"且值不为 0 就判失败，
而 `ODS 脏数据体检` 里的 `客户ID缺失 = 2067` 是**故意注入的脏数据**，
它本来就该大于 0。

**修复**：把校验分成两类——

- **硬性断言**（必须通过）：金额差额 = 0、订单数一致、维度孤儿 = 0、SCD2 唯一、数据新鲜度一致；
- **信息项**（只展示）：行数总览、月度 KPI、ODS 质量体检（后者的"通过"条件是脏数据 > 0）。

**教训**：校验规则本身也要被校验。"一键判定通过/失败"如果不能区分
"数据错了"和"数据本来就该脏"，就会变成狼来了。
